# Jemora｜AI 長篇小說多模型協作工作流

> 來源研究：MapleFeather〈AI 寫小說工作流怎麼設計？GPT、Claude、Gemini 三巨頭分工最全攻略〉（2026-09-08 更新）
> 原文：https://maplefeather.com/article/ai-novel-writing-workflow-gpt-claude-gemini-2026
>
> 本文件不是原文複製，而是依研究內容重新整理，並轉換成 Jemora／知遙小說出版工作室可直接使用的工作規範。

## 1. 核心原則

長篇小說不要把所有工作都交給同一個模型。研究文章的核心分工是：

- **ChatGPT：結構、發想、角色與大綱**
- **Claude：章節續寫、語感與修文**
- **Gemini：資料、世界觀考據與事實查證**

一句話：**結構交給 GPT、文筆交給 Claude、資料交給 Gemini。**

但 Jemora 不採取「三個模型輪流決定小說」的方式，而是維持：

> **作者／Jemora Canon > 任一 AI 模型**

模型可以提出建議、分析、草稿與校對結果，但不能自行改動已確認的角色、世界觀、時間線、人物關係、伏筆或結局。

## 2. Jemora 七階段工作流

### Phase 01｜發想
**主要工具：ChatGPT**

輸入：題材、作品定位、讀者、創作限制、作者偏好。

輸出：
- 題材方向
- 核心賣點
- 主題與情緒核心
- 主要衝突
- 可發展的故事鉤子

### Phase 02｜故事架構
**主要工具：ChatGPT**

由大到小：

1. 故事核心
2. 世界觀
3. 主線／副線
4. 三幕或多篇結構
5. 篇章目標
6. 章節 Beat
7. 場景／轉折

Jemora 額外要求：每個重大事件都必須能回答「為什麼現在發生、誰造成、造成什麼後果、下一步推進什麼」。

### Phase 03｜角色 Bible
**主要工具：ChatGPT**

每名主要角色至少建立：

- 姓名／年齡／生日
- 外貌與辨識特徵
- 性格
- 核心欲望
- 核心恐懼
- 缺陷／矛盾
- 能力與限制
- 背景
- 人物關係
- 說話方式
- 情緒觸發點
- 人物弧線
- 結局狀態

**固定規則：角色卡一旦確認，正文不可自行漂移。**

### Phase 04｜世界觀與考據
**主要工具：Gemini 或具備可靠搜尋／文件分析能力的工具**

適用於：
- 歷史
- 醫療
- 科學
- 法律
- 金融
- 地理
- 科幻技術
- 宮廷制度
- 職業細節

輸出「考據手冊」，把可驗證事實與創作虛構設定分開。

格式建議：

| 項目 | 內容 | 來源 | 信心 | 小說可用方式 |
|---|---|---|---|---|
| 時代背景 |  |  |  |  |
| 專業術語 |  |  |  |  |
| 制度／法律 |  |  |  |  |
| 地理／交通 |  |  |  |  |
| 科學／醫療 |  |  |  |  |

### Phase 05｜章節初稿
**主要工具：依需求選擇長文生成模型；研究文章偏向 Claude**

每次寫作工作包建議包含：

- Canon 摘要
- 角色 Bible
- 世界觀 Bible
- 時間線
- 本章 Beat
- 前 3～5 章必要上下文
- 文風規範
- 禁止事項
- 本章必須留下的伏筆
- 本章不得提前揭露的資訊

**重要：不要只把「上一章」丟給模型。** 長篇最容易發生的錯誤就是人物、伏筆、時間線逐章漂移。

### Phase 06｜出版級修文
**主要工具：Claude 或其他適合細修的模型**

研究文章提出一個值得保留的順序：

1. 先做節奏診斷
2. 再修句子與段落
3. 再處理 AI 腔
4. 最後人工閱讀與微調

Jemora 的出版級修文檢查：

- 劇情是否真的推進
- 場景是否有目的
- 對白是否自然且有潛台詞
- 情緒是否過早說破
- 是否過度解釋
- 是否重複同一資訊
- 人物反應是否符合角色卡
- 前後章是否矛盾
- 伏筆是否正確保留
- 回收是否過早或過晚
- 是否出現 AI 常見的制式轉折
- 是否需要人工重寫

### Phase 07｜事實查證與最終 Canon Check
**主要工具：Gemini／網路搜尋／人工核對**

涉及可查證資訊時，必須在出版前重新核對：

- 年代
- 日期
- 地點
- 科學
- 醫療
- 法律
- 金融
- 職業流程
- 歷史制度
- 技術規格

查證工具的結果不能直接覆蓋小說 Canon；若真實資料與已確認的虛構設定衝突，標記為「創作設定」或回到作者決策。

## 3. 三模型的實際分工表

| 工作 | 首選 | Jemora 使用方式 |
|---|---|---|
| 題材發想 | ChatGPT | 腦力激盪與故事方向 |
| 長篇架構 | ChatGPT | 篇章、章節、Beat、因果鏈 |
| 角色設計 | ChatGPT | Character Bible |
| 世界觀考據 | Gemini | Research Pack／考據手冊 |
| 歷史／醫療／科學查證 | Gemini | Fact Check |
| 章節續寫 | 長文生成模型 | 嚴格依 Canon 工作包輸出 |
| 文句修整 | Claude 類型工具 | 保留劇情，只處理語感與節奏 |
| 最終校對 | Jemora／人工＋AI | 全書一致性、時間線、伏筆 |

**注意：這是一種工作流建議，不是固定真理。** 模型能力與版本會更新，因此實際使用時以當前模型實測與作品需求為準。

## 4. 模型交接不能直接「複製貼上」

多模型協作最大的風險不是模型本身，而是交接時脈絡遺失。

Jemora 建議所有交接都使用「結構化交接包」：

```text
WORK_ID
作品：
篇章：
章節：
版本：

【Canon】
已確認設定：
不可修改設定：

【Characters】
本章出場角色：
人物當前狀態：

【Timeline】
上一事件：
目前時間：
下一已知事件：

【Plot】
本章目的：
本章衝突：
本章轉折：
本章結果：

【Foreshadowing】
必須保留：
可以揭露：
禁止揭露：

【Style】
文風：
敘事視角：
對白要求：
禁用表達：

【Output】
本次只允許完成：
```

這會比單純把上一段文字貼給另一個模型更穩定。

## 5. Jemora 的「不要讓 AI 自己腦補」規則

### 高風險項目

以下內容一律不得由模型自行決定：

- 主角生日
- 親屬關係
- 四姊妹關係
- 既定人物背景
- 已發生事件
- 已揭露真相
- 伏筆答案
- 結局
- 世界觀硬規則
- 作品時間線

若資料不足，模型必須標示：

> **[需要作者決策]**

而不是自行補設定。

## 6. 修文順序

推薦採用：

```text
內容正確
 ↓
劇情因果
 ↓
人物一致
 ↓
節奏
 ↓
情緒
 ↓
對白
 ↓
語句
 ↓
AI 腔處理
 ↓
出版級校對
```

不要一開始就要求「寫得更漂亮」。如果劇情、人物或節奏有問題，單純潤色只會把問題包裝得更漂亮。

## 7. 人機協作原則

研究文章最後的核心觀念值得納入 Jemora：AI 不應取代作者對故事的決策。

Jemora 定義為：

> **AI 負責加速；作者負責選擇；Canon 負責約束；出版校對負責守門。**

特別是以下場景，應提高人工介入比例：

- 關鍵感情轉折
- 核心衝突爆發
- 重大死亡／生離死別
- 重要告白
- 高張力對白
- 結局
- 伏筆揭露
- 世界觀重大反轉

## 8. 套用到《四姊妹》系列

《四姊妹》四部作品已經是既有 Canon，因此不應重新用三模型「自由創作」。應改採：

```text
既有最終修正版小說
        ↓
Canon 抽取
        ↓
Character Bible
        ↓
Relationship Bible
        ↓
Timeline Bible
        ↓
Plot / Foreshadowing Bible
        ↓
出版級校對
        ↓
場景拆解
        ↓
Scene Sheet
        ↓
Visual Bible
        ↓
Google Flow / 影音製作
```

也就是說，《局中玫瑰》《權局之下》《生死有你》《謎底之外》目前最重要的不是「換模型重寫」，而是把已完成內容轉成可供所有 Agent 讀取的 Canon 資產。

## 9. 與 Jemora Novel-to-Media Pipeline 的銜接

小說完成後：

```text
Novel Canon
   ↓
Chapter Bible
   ↓
Scene Sheet
   ↓
Character Bible
   ↓
Visual Bible
   ↓
Shot List
   ↓
Prompt
   ↓
Google Flow / Video
   ↓
Voice / Audio
   ↓
Subtitle
   ↓
Music
   ↓
Final Episode
```

AI 小說工作流與 Google Flow 工作流必須共用同一套 Canon，而不是各自重新理解角色。

## 10. 最小可行配置

### 只有一個模型
先把所有流程集中在一個模型，重點是建立固定模板與 Canon 管理。

### 兩個模型
建議：

```text
ChatGPT → 架構／角色
長文模型 → 續寫／修文
```

### 三個模型
完整配置：

```text
ChatGPT → 發想／架構／角色
Claude 類型模型 → 續寫／修文
Gemini → 考據／事實查證
```

不需要為了「看起來完整」而強制三個模型全部介入。工具越多，交接成本也越高。

## 11. Prompt Template 管理

Jemora 建議每個階段都建立固定 Prompt，而不是每次臨時重寫指令。

推薦目錄：

```text
prompts/
├── 01_發想.md
├── 02_故事架構.md
├── 03_角色Bible.md
├── 04_世界觀考據.md
├── 05_章節續寫.md
├── 06_出版級修文.md
├── 07_事實查證.md
├── 08_全書一致性校對.md
├── 09_場景拆解.md
└── 10_影片Prompt.md
```

固定模板的目的不是限制創作，而是降低品質波動與遺漏設定的機率。
